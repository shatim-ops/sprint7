Ветка с решением: `rag`

## Как запустить

```bash
git clone https://github.com/shatim-ops/sprint7.git && cd sprint7
git checkout rag

python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env        # вписать LLM_API_KEY, остальное можно не трогать

python scripts/build_corpus.py   # база знаний из исходников, с подменой терминов
python scripts/check_leaks.py    # проверка, что исходная вселенная не просвечивает
python scripts/build_index.py    # FAISS-индекс
python -m rag.cli                # консольный бот
```

Через Docker:

```bash
cp .env.example .env
docker compose up --build        # indexer соберёт индекс, затем поднимется бот на :8000
curl -s localhost:8000/ask -H 'Content-Type: application/json' \
  -d '{"question":"Как называется крупнейший космопорт планеты Кадрин?"}'
```

Тесты: `python -m pytest -q`.

## Задание 1. Исследование моделей и инфраструктуры

Полный отчёт: [docs/task1_research.md](docs/task1_research.md).

### Кто заказчик и для кого делаем

Заказчик это руководство QuantumForge: оно платит и хочет вернуть рабочее время,
которое уходит на поиск. Пользователи другие: разработчики, саппорт, аналитики
и новые сотрудники. Из этого расхождения и вырастает главное ограничение:
руководству важна стоимость и отсутствие юридических рисков, пользователю важны
скорость и ссылка на первоисточник.

Ключевое ограничение кейса: часть базы это ADR, спецификации заказных проектов и
регламенты под SOC 2. Компания работает из Финляндии и Эстонии, то есть под GDPR.
Выгружать такой корпус в публичный API нельзя.

### Сравнение LLM

| Критерий | Локальная Qwen2.5-32B | Локальная Qwen2.5-7B | Облачная GPT-5.6 Luna | YandexGPT 5 Pro |
|---|---|---|---|---|
| Качество в RAG | Достаточное | Хуже держит формат | Лучшее | Сопоставимо с 32B |
| Первый токен | 0,4 до 0,8 с | 0,2 до 0,4 с | 0,5 до 1,5 с плюс сеть | Сопоставимо |
| Стоимость | от 120 тыс. руб. в месяц за GPU | от 45 тыс. руб. в месяц | 0,20 и 1,20 долл. за 1M токенов | Порядок сопоставим |
| Развёртывание | vLLM, Kubernetes, инженер | То же, проще по памяти | Ключ и HTTP-запрос | Ключ и HTTP-запрос |
| Данные наружу | Нет | Нет | Да | Да |

При профиле 1500 запросов в день (около 110M входных и 13M выходных токенов
в месяц) облако обходится примерно в 38 долл., собственный GPU от 120 тыс. руб.
Экономического аргумента за локальный инференс нет, аргумент только юридический.

### Сравнение эмбеддингов

| Критерий | multilingual-e5-small | multilingual-e5-large | OpenAI text-embedding-3-small |
|---|---|---|---|
| Размерность | 384 | 1024 | 1536, можно урезать |
| Скорость индексации | около 900 чанков в минуту на 4 vCPU | около 200 на CPU | ограничена API |
| Качество на русском | Рабочее | Заметно лучше | Сопоставимо с e5-large |
| Стоимость | 0 | 0, но нужен GPU на объёме | около 0,02 долл. за 1M токенов |
| Данные наружу | Нет | Нет | Уходит весь корпус |

Принципиальная разница с LLM: при облачных эмбеддингах наружу уходит не отдельный
запрос, а вся база знаний целиком, все 18 тысяч файлов и 3 тысячи страниц.
Локальная модель снимает этот риск практически бесплатно.

### Сравнение векторных БД

| Критерий | FAISS | ChromaDB |
|---|---|---|
| Тип | Библиотека в процессе приложения | Отдельный сервис с REST API |
| Скорость поиска | Единицы миллисекунд на 100 тыс. векторов | Сопоставима, HNSW |
| Индексация | Ограничена только эмбеддингами | Медленнее, пишет на диск |
| Фильтрация по метаданным | Нет, хранить рядом самому | Есть из коробки |
| Обновление документов | Проще перестроить индекс | upsert и delete по id |
| Эксплуатация | Файл рядом с приложением | Ещё один сервис в контуре |
| Стоимость владения | Память процесса | Контейнер, диск, бэкапы |

Выбран **FAISS**: на объёме пилота выигрыш ChromaDB в фильтрации не нужен, а
эксплуатационные издержки появляются сразу. Когда потребуются права доступа,
инкрементальное обновление и несколько реплик, правильный шаг это Qdrant,
а не ChromaDB: он даёт и фильтрацию по payload, и репликацию.

### Конфигурация сервера

4 vCPU, 8 ГБ RAM, 50 ГБ SSD, без GPU. Модель эмбеддингов занимает около 500 МБ,
индекс на 100 тыс. чанков по 384 float32 около 150 МБ. GPU понадобился бы только
при локальной LLM: A100 40 ГБ для 32B в fp16 или L4 для 7B в квантизации.

### Варианты и выбор

| Вариант | Стоимость в месяц | Юридический риск | Сложность | Время до пилота |
|---|---|---|---|---|
| A. Всё в облаке | около 40 долл. | Высокий | Низкая | 1 день |
| B. Всё локально | от 120 тыс. руб. | Отсутствует | Высокая | 2 недели |
| C. Локальные эмбеддинги плюс облачная LLM | около 40 долл. | Средний | Низкая | 2 дня |
| D. Гибрид с разделением контуров | около 60 тыс. руб. | Низкий | Средняя | 1,5 месяца |

**Выбран вариант C.** Корпус не покидает периметр, наружу уходят только
релевантные фрагменты и только в момент запроса. Инфраструктура это один
контейнер без GPU. Совместимость с протоколом OpenAI оставляет возможность за
день переехать на локальный vLLM, если безопасность запретит внешний вызов.

Вариант D это правильная целевая архитектура, но он требует классификации
18 тысяч файлов по уровню конфиденциальности, которой в компании сейчас нет.

### Итоговый выбор векторной БД

**FAISS**, индекс `IndexFlatIP` по нормированным векторам, то есть точный поиск
по косинусной близости без приближений. На нашем объёме это доли миллисекунды и
ноль настроек. Метаданные чанков лежат рядом в `index/chunks.json`.

## Задание 2. Подготовка базы знаний

Подробно: [docs/knowledge_base.md](docs/knowledge_base.md).

**Предметная область:** вселенная Star Wars, справочные материалы
ru.starwars.fandom.com. Выбрана потому, что модель знает её наизусть, и любой
ответ по памяти вместо ответа по индексу будет сразу заметен.

**Что сделано:**

1. Собраны 44 документа по ключевым сущностям: персонажи, планеты, корабли,
   технологии, организации, события. Один файл на сущность, лежат в `source_raw/`.
2. Составлен словарь замен `terms_map.json`, 287 правил.
3. Скрипт `scripts/build_corpus.py` применяет замены и пишет результат в
   `knowledge_base/`. Имена файлов тоже собираются из новых заголовков.
4. Скрипт `scripts/check_leaks.py` проверяет результат по стоп-листу из 189
   слов и основ исходной вселенной. Проверка вынесена в тест.

**Логика подмены.** Наивная замена по подстроке на русском не работает, учтены
три вещи: склонение (замена подбирается с тем же типом основы, иначе ломается
падеж), границы слова (иначе "Мол" находится внутри "молодой", при этом дефис
границей считается, чтобы отрабатывал "мастер-джедай") и регистр (заменяется
"Сила" как название явления, но не "силой мысли"). Правила применяются от
длинных ключей к коротким, иначе короткое правило съедает часть длинного.

Примеры соответствий:

| Было | Стало |
|---|---|
| Дарт Вейдер | Вран Велгор |
| Люк Скайуокер | Деран Кестрел |
| Звезда Смерти | Цитадель Рока |
| Сила | Вейра |
| Татуин | Кадрин |
| Орден джедаев | Орден сайферов |

**Результат:** 44 документа в `knowledge_base/`, словарь `terms_map.json`,
скрипт сборки и скрипт проверки. Стоп-лист чист, то есть по памяти модель
ответить не сможет.

## Задание 3. Векторный индекс

Подробно: [docs/index_report.md](docs/index_report.md).

**Модель эмбеддингов:** `intfloat/multilingual-e5-small`
(https://huggingface.co/intfloat/multilingual-e5-small), 384 измерения,
работает локально на CPU. Для семейства e5 обязательны префиксы `query:` и
`passage:`, без них качество заметно хуже, в коде это учтено.

**Чанкинг:** `RecursiveCharacterTextSplitter` из LangChain, 700 символов с
перекрытием 120, разделители от крупных к мелким: заголовок раздела, пустая
строка, перенос, точка, пробел. Резать по разделам, а не по символам наугад,
важно потому, что иначе цитата в ответе получается обрывком фразы.

**Метаданные чанка:** `chunk_id`, `doc_id`, `title`, `category`, `path`,
`position`. Этого достаточно, чтобы бот сослался на документ и раздел.

**Индекс:** FAISS `IndexFlatIP` по нормированным векторам, файл
`index/faiss.index`, метаданные `index/chunks.json`, статистика сборки
`index/index_stats.json`.

**Код:** `scripts/build_index.py`, модули `rag/chunking.py`,
`rag/embeddings.py`, `rag/vectorstore.py`.

## Задание 4. RAG-бот с техниками промптинга

**Пайплайн** собран в `rag/pipeline.py`:

1. Вопрос переводится в вектор тем же энкодером, что и документы.
2. Поиск ближайших чанков в FAISS, `top_k = 4`.
3. Найденные чанки проходят фильтр инъекций.
4. Чанки ниже порога релевантности отбрасываются. Если не осталось ни одного,
   бот отвечает "Я не знаю" и к модели не обращается вообще.
5. Собирается промпт: системная инструкция, few-shot примеры, контекст, вопрос.
6. Запрос уходит в LLM через OpenAI-совместимый эндпоинт.
7. Ответ разбирается на рассуждение, ответ и источники, проходит постпроверку.

Готовую цепочку `RetrievalQA` я сознательно не брал. Она прячет промпт внутри
себя, а в этом задании как раз промпт и есть предмет работы: нужно управлять
few-shot примерами, форматом рассуждения и системными ограничениями. Компоненты
LangChain при этом используются там, где они полезны, то есть в чанкинге.

**Few-shot.** Два примера в `rag/prompts.py`. Первый показывает нормальный ответ
с опорой на документ, второй показывает отказ. Факты в примерах взяты из той же
базы знаний, и на это есть тест: `tests/test_prompts.py` проверяет, что Сайрон
действительно упоминается в документе о планете Кадрин. Пример с отказом нужен
не меньше первого: без него модель почти никогда не говорит "не знаю".

**Chain-of-Thought.** Системный промпт требует формата "Рассуждение, затем
Ответ, затем Источники". Рассуждение просит не абстрактных размышлений, а
конкретики: на какой фрагмент опираемся и какой вывод из него следует.
Пайплайн разбирает ответ регуляркой и хранит рассуждение отдельно от ответа,
поэтому в API можно отдавать только ответ, а рассуждение оставлять в логе.

**Интерфейсы:** консольный REPL `python -m rag.cli` и HTTP API на FastAPI
(`rag/api.py`, эндпоинты `/ask` и `/health`).

**Примеры диалогов** и случаи отказа: [docs/demo_log.md](docs/demo_log.md).

## Задание 5. Запуск и демонстрация

Подробно: [docs/security.md](docs/security.md), протокол прогона:
[docs/demo_log.md](docs/demo_log.md).

**Вредоносный документ** `knowledge_base/injected/incident_note.txt` попадает в
индекс наравне с остальными, никаких исключений при сборке для него нет.

**Слои защиты:**

1. Системный промпт: текст контекста это данные, а не команды.
2. Фильтрация чанков до сборки промпта по набору паттернов инъекций. Основной
   рабочий слой: чего нет в промпте, того модель не выполнит.
3. Очистка отдельных строк, если фрагмент в целом полезен.
4. Постпроверка ответа: сверка с заблокированными фрагментами по совпадению
   словосочетаний и проверка на признаки учётных данных.

Защита выключается переменной `GUARD_ENABLED=false`, и в логе есть контрольный
прогон того же вопроса без защиты.

**Прогон:** 10 обращений, 5 с ответом из базы и 5 с отказом или фильтрацией,
плюс контрольный. Команда `python scripts/demo.py`.

**Выводы.** Фильтрация чанков отрабатывает и прямую формулировку атаки, и
косвенную через слово из вредоносного документа, потому что решение принимается
до обращения к модели. Порог релевантности честно отсекает вопросы, которых в
базе нет.

Что остаётся уязвимым: фильтр построен на списке паттернов и не поймает
переформулированную инъекцию, косвенные атаки через кодирование не проверяются
вообще, а постпроверка на учётные данные даст ложные срабатывания на документах,
которые легитимно описывают работу с паролями. Но самый большой разрыв не в
инъекциях: у бота нет разграничения прав доступа, и сейчас любой пользователь
видит любой документ базы. Для компании с закрытыми ADR это и нужно закрывать
первым, а правильный способ это переход на векторную БД с фильтрацией по
метаданным.
